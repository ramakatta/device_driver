Classic ARM SoC (e.g. STM32MP2):
BootROM → TF-A BL1 → TF-A BL2 → BL31 → U-Boot → Linux

Raspberry Pi 4:
GPU firmware (start4.elf) → TF-A BL31 (armstub8.bin) → U-Boot → Linux
Why bother with TF-A on RPi4?

Most RPi4 tutorials skip TF-A entirely. Copy a kernel8.img to a FAT partition, add a config.txt, and U-Boot starts. Simple.

But on a real embedded product — an automotive ECU, a medical device, a drone flight controller — TF-A is not optional. It provides three things that matter in production:

PSCI is the ARM standard for CPU power management. Without it, reboot and shutdown do not work correctly on ARM. The kernel calls into BL31 via SMC instructions whenever it needs to manage CPU power states.

CPU errata workarounds are silicon bug patches applied at EL3 before Linux runs. The Cortex-A72 has several known errata. TF-A applies the workarounds automatically during initialization.

Build TF-A

git clone https://git.trustedfirmware.org/TF-A/trusted-firmware-a.git
cd trusted-firmware-a
git checkout v2.10.0

make \
  CROSS_COMPILE=aarch64-linux-gnu- \
  PLAT=rpi4 \
  RPI3_PRELOADED_DTB_BASE=0x2600000 \
  PRELOADED_BL33_BASE=0x80000 \
  SUPPORT_VFP=1 \
  DEBUG=1 \
  all
trusted-firmware-a/build/rpi4/debug/bl31.bin
sudo cp trusted-firmware-a/build/rpi4/debug/bl31.bin /mnt/armstub8.bin




Build U-boot

git clone https://gitlab.denx.de/u-boot/u-boot
cd u-boot
git checkout v2023.01
make CROSS_COMPILE=aarch64-linux-gnu- rpi_4_defconfig
make CROSS_COMPILE=aarch64-linux-gnu- menuconfig
make CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)
ls -lh u-boot.bin
# u-boot.bin  603K
cp u-boot.bin kernel8.img


sudo tee /mnt/config.txt << 'EOF'
arm_64bit=1
enable_uart=1
dtoverlay=disable-bt
armstub=armstub8.bin
kernel=kernel8.img
device_tree_address=0x2600000
EOF

Config.txt in bootfs 0 partition

# Run in 64-bit mode
arm_64bit=1
enable_uart=1
enable_gic=1
dtoverlay=disable-bt
armstub=bl31.bin
# Force the Pi to boot your U-Boot binary instead of the Linux kernel
kernel=u-boot.bin
device_tree_address=0x2600000
